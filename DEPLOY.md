# Dokploy deployment

This follows Octo Flow's Dokploy layout: one Compose application, separate public web and API domains, and an external PostgreSQL database.

## Configure Dokploy

1. Create a PostgreSQL database reachable from the Dokploy server.
2. Create a **Docker Compose** application from this repository and select `compose.dokploy.yml` as the Compose file.
3. Add these variables in the application's **Environment** tab:

   ```env
   DATABASE_URL=postgresql://USER:PASSWORD@HOST:5432/DBNAME?sslmode=require
   UPDATER_TOKEN=replace-with-a-long-random-secret
   CORS_ORIGINS=https://app.example.com
   VITE_API_BASE_URL=https://api.example.com
   UPDATER_API_URL=https://api.example.com
   MCP_ALLOWED_HOSTS=api.example.com
   ALLOW_OPEN_REGISTRATION=True
   # Optional: enables AI-generated answers
   OPENROUTER_API_KEY=
   LLM_MODEL=google/gemini-3.5-flash-lite
   # Affinebot and GitHub (see README: "Connecting Affinebot" and "GitHub")
   AFFINEBOT_TIMEOUT_S=10
   # Recommended: encrypts stored Affinebot link tokens (empty = plain text)
   UPDATER_SECRET_KEY=replace-with-a-long-random-string
   GITHUB_WEBHOOK_SECRET=replace-with-the-github-app-webhook-secret
   ```

4. Attach `app.example.com` to the `web` service on container port **80**, and `api.example.com` to the `api` service on container port **8000**. Enable HTTPS for both domains. Replace the example origins above with these exact public origins (no trailing slash). `MCP_ALLOWED_HOSTS` must contain the public API hostname (bare hostname is enough — the server also accepts any port on it), otherwise every `POST /mcp` through Cloudflare/Dokploy is rejected with `421 Invalid Host header` before any MCP logic runs. `UPDATER_API_URL` is a fallback for the same check.
5. Deploy the stack. The API creates its tables on startup; it needs a database user allowed to create tables. If `MCP_ALLOWED_HOSTS` was missing on a previous deploy, redeploy after setting it — reloading the MCP client alone cannot fix a `421`.

`VITE_API_BASE_URL` is baked into the frontend at build time. Redeploy the stack after changing it. Keep `DATABASE_URL`, `UPDATER_TOKEN`, and `OPENROUTER_API_KEY` in Dokploy, outside Git. After deploying, open the web UI and create an account, then issue per-agent API keys from the sidebar — agents use a key as `Authorization: Bearer upk_…`, revocable without touching other agents. Once an account exists you may empty `UPDATER_TOKEN` and redeploy to run on logins + keys only; set `ALLOW_OPEN_REGISTRATION=False` to close sign-ups.

If the `web` image build fails with `npm error Missing: @emnapi/... from lock file`, the lock was regenerated by a newer npm (11+) that prunes Tailwind's bundled wasm entries. The Dockerfile falls back to a lock-repairing `npm install`, so the deploy still succeeds; to keep `package-lock.json` clean, regenerate it with the image's npm 10:

```bash
docker run --rm -v "$PWD/frontend":/app -w /app node:22-bookworm-slim npm install --package-lock-only
```

### Affinebot and GitHub

The Affinebot link (base URL, client id and token) is entered per workspace in **Settings > Integrations**, not in Dokploy. Keep no GitHub token in Dokploy; repos and issues come from the Affinebot GitHub App.

- Delegated tasks run on each user's own agent over MCP, so no callback URL or secret is needed.
- In the GitHub App, set the webhook URL to `https://api.example.com/api/github/webhook`, with the same secret as `GITHUB_WEBHOOK_SECRET`. Subscribe to `issues` and `pull_request`.
- The App needs Metadata: read, Issues: read & write, Pull requests: read & write and Contents: read & write. Re-approve after any permission change.

## Verify

```bash
curl -f https://api.example.com/api/health
curl -f https://app.example.com/healthz
```

Open the web domain, enter the configured token, and confirm the updates view loads. The health endpoint checks that the API process is serving requests; it does not check PostgreSQL connectivity.
