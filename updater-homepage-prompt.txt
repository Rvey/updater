Build a polished, fun, production-ready marketing homepage for “Updater”, an open-source shipping memory for work completed with coding agents.

PROJECT CONTEXT

Updater helps developers preserve the story behind shipped code. After a coding agent finishes and verifies a feature, it publishes a structured update over MCP containing what changed, why it was needed, how it works, expected impact, tradeoffs, relevant files, branch, commit, pull request, tags, and learning notes. The developer gets a searchable record of shipped work instead of losing important context across agent chats, commits, and pull requests.

The homepage should make this idea understandable in under ten seconds:

“Your coding agent writes the code. Updater remembers why it shipped.”

Primary audience: developers and small engineering teams using Codex, Claude Code, Cursor, or OpenCode.

Primary action: connect an agent with the one-line CLI command.
Secondary action: view the project on GitHub.

VISUAL THESIS

Create an editorial developer-tool homepage that feels like a playful shipping log crossed with a clean terminal. Use a warm off-white canvas, near-black ink, and electric lime as the single accent color. The visual language should feel fast, clever, trustworthy, and slightly mischievous—not corporate, cyberpunk, or like a generic SaaS template.

Treat the first viewport like a poster. Make “Updater.” the loudest brand element. Use oversized type, confident spacing, subtle grid lines, terminal details, and the real product screenshot as the dominant visual. Keep the page mostly cardless. Use full-width sections, dividers, columns, sticky storytelling, and large media instead of a grid of floating rounded cards.

Suggested palette:
- Canvas: #F7F7F2
- Ink: #22241F
- Muted ink: #666A61
- Hairline: #DFE1D8
- Lime accent: #B8F34A or a similarly vivid accessible lime
- Dark section: #20231E
- White: #FFFFFF

Typography:
- Use Geist or a similarly crisp grotesk for headings and brand.
- Use Inter for body copy.
- Use a readable monospace face for commands, labels, file paths, and metadata.
- Maximum two primary font families plus monospace.

Add a very subtle paper/noise texture and faint repository-grid lines, but preserve excellent contrast. Avoid glossy 3D blobs, purple gradients, excessive shadows, glassmorphism, stock photography, fake testimonials, fake customer logos, and invented usage statistics.

INTERACTION THESIS

Use restrained motion with three memorable moments:
1. On load, reveal the brand, headline, command line, and screenshot in a quick stagger. A small lime “shipped” status dot can blink once, then remain steady.
2. In the “How it works” section, use a sticky vertical story. As the user scrolls through the four steps, animate a line traveling from agent → MCP → ship log → future context.
3. Make every CLI command block genuinely copyable. On click, change “Copy” to “Copied ✓” briefly. Give screenshot frames a subtle 1–2 degree tilt or depth shift on scroll, but keep text and controls still and readable.

Respect prefers-reduced-motion. Make all interactions keyboard accessible. Do not animate continuously except for an optional very subtle terminal cursor.

5. HOW IT WORKS — STICKY FOUR-STEP FLOW

Section label:
FROM VERIFIED CODE TO SHARED MEMORY

Headline:
Ship once. Understand it later.

Build a sticky, scroll-driven workflow with four numbered steps on one side and a simple animated pipeline on the other. The pipeline should read: Coding agent → MCP → Updater → Future question.

Step 01 — Finish and verify
Your coding agent completes a feature, runs the relevant checks, and confirms the work is ready.

Step 02 — Publish the story
Before replying, the agent calls Updater over MCP and sends the what, why, how, impact, tradeoffs, files, branch, commit, and pull request.

Step 03 — Search the ship log
The update appears in a focused workspace where you can browse by repository, search instantly, add notes, and keep related questions attached.

Step 04 — Learn over time
Record observed impact, revisit decisions, or ask the connected agent for focused code context without giving the app full repository access.

End the section with a small terminal event sequence:
$ feature verified
✓ publish_feature
✓ update saved
✓ context available later

RESPONSIVE BEHAVIOR

- Desktop: wide editorial compositions, large screenshot surfaces, and sticky workflow storytelling.
- Tablet: preserve the hierarchy while stacking text and media where necessary.
- Mobile: keep the first screen focused on brand, headline, command, and primary CTA. Screenshots may scroll horizontally inside an accessible viewport if shrinking them would make the UI unreadable.
- Use fluid typography with clamp().
- Keep tap targets at least 44px.
- Prevent horizontal page overflow.
- Do not hide meaningful content or the CLI command on small screens.

ACCESSIBILITY AND QUALITY

- Use semantic HTML landmarks and a logical heading hierarchy.
- Ensure WCAG AA color contrast, including lime treatments.
- Add descriptive alt text for every screenshot.
- Provide visible keyboard focus states.
- Make copy buttons announce success to assistive technology.
- Respect reduced-motion preferences.
- Optimize real screenshots and lazy-load those below the fold.
- Avoid layout shift and oversized client-side animation bundles.
- Keep navigation, command copy actions, anchor links, and GitHub/API links functional.

IMPLEMENTATION GUARDRAILS

- Use the project’s existing React, TypeScript, Vite, Tailwind CSS, and shadcn/ui setup.
- Reuse the existing logo and real screenshots. Do not fabricate a different application UI.
- Preserve the established Geist/Inter typography and zinc/lime product identity.
- Prefer clean layout primitives over excessive component abstractions.
- Do not use a generic feature-card mosaic.
- Do not invent testimonials, company logos, customer counts, GitHub stars, uptime claims, performance numbers, or pricing.
- Do not add a pricing section; Updater is presented as open source and self-hostable.
- Do not claim the service stores an entire codebase.
- Keep copy concise and use the exact product facts provided here.
- The finished page should feel fun because of typography, rhythm, terminal micro-interactions, and motion—not jokes, mascots, clutter, or novelty UI.

FINAL ACCEPTANCE CHECK

The finished homepage must answer, in order:
1. What is Updater?
2. Why was it created?
3. How does it fit into agent-assisted coding?
4. What exactly does it save and help users do?
5. How does code-context access preserve privacy?
6. Which agents does it support?
7. How can someone connect it in one command?
8. Is it open source, self-hostable, and easy to contribute to?

The overall impression should be: “This is a sharp, useful developer tool I understand immediately—and I want to paste that command.”
